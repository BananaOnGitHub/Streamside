# Secure investigation configuration updates — v2 architecture and milestone

Status: required future Streamside capability; implementation plan, not an
implemented updater. Recorded 2026-10-26. This work is separate from the
[v1 completion audit](DIAGNOSTIC_INFRASTRUCTURE_COMPLETION_AUDIT.md).
F1–F6 remain authoritative for v1. Finishing v1 does not retire this milestone.

## Objective and boundaries

After one ordinary development runtime ships the updater and trusted root,
Streamside must retrieve, authenticate, admit, cache and explicitly activate a
new reviewed configuration from GitHub without rebuilding/reinstalling Twitch,
provided its requested capabilities and semantic versions already exist in the
installed binary. Demonstrating retrieval of identical pinned bytes does not
meet this objective.

Remote authorization changes configuration bytes, never executable authority.
No downloaded JavaScript, Hermes bytecode, Objective-C selector, function ID,
address, hook offset, arbitrary property path, data field, formatter or network
destination may reach a runtime command. Signed input is still untrusted input.
An authentic but incompatible or over-budget configuration must be rejected.

This task implements no updater, signing service, production key, retrieval,
persistent remote cache, publication or autoactivation. Public feature/release
documentation stays at its supported scope until acceptance.

## Existing interfaces and migration

The original inputs are the full proposal and both implementation briefs
identified by digest in the v1 audit. The local brief's event-first,
long-session recorder requirements supersede the proposal's snapshot-only and
60-second armed lease. The briefs defer signed updates; this milestone makes
their future implementation explicit rather than dropping it.

| Current interface | v2 use / necessary change |
| --- | --- |
| tas_inv_parse and TASInvManifest | Keep the legacy schema-1 bundle path unchanged and reuse its bounded reader/constraint checks. V2 adds a schema-2 selected-configuration envelope for bounded authenticated configuration IDs plus the same numeric options. The current hardcoded investigation ID is not a reusable generic catalog API. Parse success is never authenticity. |
| tas_inv_capability, tas_inv_donor_matches, native profile and source admission | Retain exact donor/ABI/source/installed-hook intersection. A signature cannot enable missing code or relax these gates. Capability semantic expansion requires a new compiled version. |
| tas_inv_begin / ack / pending command / generation / copied manifest | Retain Arm/Capture/Stop enums and the bounded 16-number JS command parameters. No raw signed JSON is sent to Hermes. An Arm pins one native manifest/identity for its lifetime. |
| tas_inv_registry | Retain as the independent exact-byte bundled fallback validator. Do not remove its SHA pin or turn its optional same-byte cache argument into an unauthenticated alternate-manifest entry. |
| tas_inv_configuration added during v1 hardening | Read-only copied selection/digest/source accessor. It decouples UI/report consumers from the generated byte-array header. It does not install a configuration. |
| F2 native capture metadata and F3 immutable export copy | Preserve captured identity even after refresh, selection, Stop or host replacement. Later add a versioned bounded provenance extension for TUF versions/digests, authorization identity and expiry. No report-to-updater data path. |
| Current schema's rn-chat-gaps ID and v4 numeric/snapshot profiles | V1 remains fixed to this ID/profile. | Current coordinator's private built-in config | V2 needs a narrowly owned, internal authenticated-selection transaction. This is new v2 source work, not implemented by F1–F4. Permit replacement only while Dormant with no pending command, after authentication plus native admission; copy value and identity atomically. |
| Current UI | Add registry states and explicit refresh/select/download actions in v2. Keep Arm/Capture/Stop and general presets independent. |

The only v1 compatibility provisions are copied configuration identity,
capture-pinned provenance, immutable export copies and preserved parsing/trust
separation. There is no v1 “trusted=true” flag, remote setter, unverified-loader
callback, production test key or reserved URL path that could bypass the pin.

Initial v2 installation still requires a normal Streamside update: v1 contains
neither a public-key root nor a verifier/updater. That one bootstrap cannot
legitimately be retrofitted by a manifest. Subsequent compatible configurations
must meet the no-rebuild demonstration in M6 below.

## Trust boundaries

~~~mermaid
flowchart LR
  Review["Reviewed config source"] --> Offline["Independent offline root / targets signers"]
  CI["Restricted snapshot / timestamp signer"] --> Publish["Publication of signed TUF metadata"]
  Offline --> Publish
  Publish --> Host["UNTRUSTED GitHub / CDN / files"]
  Binary["Trusted installed binary: root, transport policy, capabilities, ceilings"] --> Verify
  Host --> Transport["Bounded HTTPS transport"]
  Transport --> Verify["TUF verifier: role signatures, versions, time, hashes"]
  Verify --> Cache["Verified security state + atomic candidate cache"]
  Cache --> Admit["Strict native manifest and donor/capability admission"]
  Binary --> Admit
  Admit --> Select["Dormant selection: explicit local user action"]
  Select --> Commands["Existing fixed Arm / Capture / Stop channel"]
  Commands --> Runtime["Already compiled observation runtime"]
  Runtime --> Evidence["Immutable local capture / explicit export"]
  Store["OS-protected trusted version/time state"] <--> Verify
~~~

The updater has no evidence-export interface. Network requests use only
compiled repository paths plus bounded authenticated target names/commit IDs.
They must never include capture rows, labels, report files, drafts, room/user
identities, tokens or diagnostics. No upload is part of refresh or verification.

Trust assumptions: the installed binary/bootstrap root, OS execution and
protected storage, Ed25519/SHA-256 implementations, and the required signing
threshold remain trustworthy. GitHub writers, Actions jobs, CDN nodes, TLS
responses, release locators and downloaded/cache files are not signing
authorities. A fully compromised process/OS or compromised root threshold
cannot be repaired by verifying its own attacker-controlled data.

## Protocol choice and library gate

Use standard TUF root/timestamp/snapshot/targets metadata with consistent
snapshots and Ed25519 role keys. Do not implement a parallel sign-one-JSON
protocol. The [TUF specification](https://theupdateframework.github.io/specification/latest/)
is the protocol reference; version 1.0.37 was inspected for this plan.
Implementation must pin its specification/library/test-suite versions.

This is a proposed standard-TUF client with a restricted Streamside repository
profile, not a claim of an already conformant implementation. Passing one
signature test, using a TUF-named package or borrowing role names is
insufficient. The shipped client core and its storage/transport integration
must pass the applicable mandatory [TUF conformance tests](https://github.com/theupdateframework/tuf-conformance).
Any simplified alternative must be explicitly named TUF-inspired, document its
lost guarantees and receive a separate design decision; it cannot silently
replace this milestone.

Library shortlist and concrete decision gate:

| Candidate | Intended use / evaluation |
| --- | --- |
| Rust tough through a small owned C ABI | Preferred feasibility candidate. Its documented loader exposes bounded transport, limits, persistent datastore and expiry enforcement. Prove iOS static linking, Ed25519/canonical metadata support, cancellation, resource fit, rollback persistence and current conformance before adoption. No audit or iOS support result is claimed here. |
| sigstore-tuf | Alternative Rust client candidate; evaluate dependency/FFI/resource profile and the pinned version's conformance, not just the project's latest report. |
| python-tuf | Independent reference oracle and publication/test tooling. Embedding Python in the injected runtime is not the proposed deployment. |
| go-tuf | Reference/interoperability candidate; Go runtime/toolchain footprint makes it a secondary injected-client choice. |
| rust-tuf | Its upstream beta/API warning is an adoption risk; do not assume stable production suitability. |

[Tough loader documentation](https://docs.rs/tough/latest/tough/struct.RepositoryLoader.html)
describes the transport/datastore/expiry controls; its unsafe expiry mode must
not be used. [Python ngclient](https://theupdateframework.readthedocs.io/en/latest/api/tuf.ngclient.html)
provides a reference workflow. [Sigstore's client documentation](https://docs.rs/sigstore-tuf/latest/sigstore_tuf/)
and [rust-tuf's own warning](https://github.com/theupdateframework/rust-tuf)
inform the alternatives. None has been installed or ported by this design.

M0 must select and pin a library plus its crypto backend, reviewed licenses,
security history, dependency lockfile and reproducible artifacts. Ed25519 must
come from that established backend, not a new implementation or CommonCrypto's
SHA function. C/FFI input/output ownership and errors are bounded, with no panic
or exception unwinding into Twitch. Transport and persistent-state callbacks
must not escape the compiled policy. If cross-compilation or resource fit
fails, stop M0 and record the dependency blocker; do not weaken trust checks or
install a scripting runtime to bypass it.

## Keys, signing authorization and exact bytes

Proposed production role policy, to be finalized in the M1 signing ceremony:

| Role | Initial threshold | Custody / function |
| --- | --- | --- |
| Root | 2 of 3 Ed25519 keys | Offline, independently stored devices/backups; authorize role keys and rotations. Distinct custodians where available. Three files under one GitHub credential are not independent custody. |
| Targets | 2 of 3 separate Ed25519 keys | Offline review authorization for configuration/catalog bytes. Repository write access and ordinary CI cannot exercise this threshold. |
| Snapshot | 1 of 1 dedicated key | Restricted signer binds approved targets metadata versions/hashes. Separate principal from repository write credentials and timestamp signing. |
| Timestamp | 1 of 1 dedicated key | Restricted online signer; short validity. Cannot authorize new target bytes without targets authorization. |

Count distinct authorized public keys toward a threshold. Duplicate signatures,
aliases for the same public key, unauthorized keys or wrong-role signatures
cannot satisfy multiple signers. Do not reuse keys across roles, repositories
or development/release trust channels. If independent custody cannot actually
be established, record that operational limitation instead of claiming it.

Embed a reviewed initial root.json and its identity in the installed binary,
including authorized public keys, role thresholds and protocol versions.
Never fetch the bootstrap key from the same untrusted GitHub response being
authenticated. The IPA/binary's authenticated distribution is the out-of-band
bootstrap; private signing keys never ship.

Exact representation:

- Standard TUF signatures cover the UTF-8 canonical JSON bytes of the signed
  object, using the chosen TUF library's specified canonicalization. They do
  not sign a pretty-printed document, an NSURLSession-decoded string, a JSON
  parser's incidental ordering, or the outer signatures array.
- Do not prepend a home-made context prefix to standard TUF signatures: that
  would break protocol interoperability. Role separation uses the verified
  _type, role-specific authorization and dedicated repository/channel keys.
  Application domain separation additionally requires the authenticated catalog
  domain streamside/investigations/v2, compiled repository identity and channel.
- Manifest/catalog target hashes and lengths cover their exact original bytes,
  including whitespace. Hash verification against authenticated targets metadata
  precedes native manifest/catalog parsing and admission.
- Metadata must undergo bounded structural parsing to verify its signatures;
  this necessary pre-verification parsing confers no trust or activation.
  Rejection must cover duplicate-key ambiguity, malformed encodings, bad
  signatures, unsupported algorithms and integer/type ambiguities.
- Metadata versions are positive bounded integers; production policy uses at
  most 2^31−1. Manifest versions retain their native uint32 bounds. Signing tools
  and client must agree on canonical Unicode/escape/integer behavior through
  shared and negative vectors.
- Include vectors with reordered JSON members, changed signed values, changed
  target whitespace, duplicate keys, wrong domain/channel/root, and signatures
  from another role or repository. A valid signature alone does not grant
  another application/channel's authorization.

The code-signing/Sigstore identity of a GitHub workflow is not a targets key.
Independent offline authorization remains necessary even if publication
provenance looks correct.

## Metadata and target format proposal

Use the standard TUF envelope, with schema-specific fields left to the library:

~~~json
{
  "signatures": [{"keyid": "<authorized-key-id>", "sig": "<Ed25519-signature-hex>"}],
  "signed": {
    "_type": "targets",
    "spec_version": "1.0.37",
    "version": 12,
    "expires": "<UTC timestamp>",
    "targets": {
      "registry/catalog.json": {
        "length": 1024,
        "hashes": {"sha256": "<exact-raw-byte-digest>"},
        "custom": {
          "streamside_domain": "streamside/investigations/v2",
          "repository": "BananaOnGitHub/Streamside",
          "channel": "development",
          "source_commit": "<full-40-hex-targets-commit>"
        }
      },
      "investigations/rn-chat-focused/6.json": {
        "length": 2048,
        "hashes": {"sha256": "<exact-raw-byte-digest>"},
        "custom": {
          "streamside_domain": "streamside/investigations/v2",
          "repository": "BananaOnGitHub/Streamside",
          "channel": "development",
          "source_commit": "<same-targets-commit>"
        }
      }
    }
  }
}
~~~

These are illustrative templates, not signed production data. Root metadata
contains standard public-key/role/threshold bindings; timestamp binds the
snapshot's version, length and SHA-256; snapshot binds targets' version, length
and SHA-256. Set consistent_snapshot=true. Versioned metadata names and
hash-prefixed target filenames are derived by the library; referring metadata
uses logical target names, not a rewritten name invented by the app.

The authenticated catalog is a strict application target:

~~~json
{
  "schema_version": 1,
  "domain": "streamside/investigations/v2",
  "repository": "BananaOnGitHub/Streamside",
  "channel": "development",
  "catalog_version": 12,
  "authorization_id": "<root-authorized-targets-key-set-identity>",
  "entries": [{
    "id": "rn-chat-focused",
    "manifest_version": 6,
    "path": "investigations/rn-chat-focused/6.json",
    "length": 2048,
    "sha256": "<same-target-digest>"
  }],
  "revoked_sha256": []
}
~~~

catalog_version equals the authenticated top-level targets metadata version.
authorization_id is SHA-256 of the TUF library's canonical UTF-8 JSON for
{domain, repository, channel, threshold, keys}, where domain is the fixed
application domain, keys maps sorted authorized targets key IDs to their full
standard key objects, and threshold is that root role's value. Check the result
against the currently verified root, never against the catalog's assertion
alone. This is an identity hash, not another signature format.

All catalog objects disallow unknown fields; IDs/paths/arrays/strings are
bounded. Entry digest/length must agree with that target in the same verified
targets metadata. A catalog cannot supply a URL, key, capability definition
or executable field. authorization_id is checked against the role identity
derived from the verified root; it is not self-authorizing.

Remote targets use a separately versioned schema 2. Reuse the current bounded
native reader/constraint validators, compiled capability/profile names, exact
donor build/HBC/ABI bindings, selected event families and bounded parameters.
Add a bounded configuration ID (`[a-z0-9][a-z0-9-]{0,63}`) to a native selection
envelope containing the existing numeric options and authenticated identity.
Reject duplicate IDs/paths in the catalog. ID and revision must match the
signed catalog and manifest, but the ID itself need not be compiled into the
binary: it names configuration data, not a new capability or executable path.
Keep the legacy schema-1 pinned bundle parser intact; reject unsupported future
schema/semantic versions. This schema-2 parser is v2 implementation work, not
an F1–F4 compatibility bypass.
 A concrete no-rebuild example is a newly reviewed ID or higher manifest revision
that selects existing translation/emission/list events, omits optional reward
observation and lowers entry/rate limits. It cannot add a new event adapter,
relax the 2 ms callback allowance or extend a donor profile.

Keep semantic manifest revisions immutable. Same ID/revision with different
bytes is a rejection, even if both have signatures. A deliberate parameter
rollback is published as a new higher revision. UI/report identity includes the
authorization era as well as ID/revision/digest; numbers from different trust
eras are not interchangeable.

No metadata file needs to contain its own Git commit/hash. Commit the target
files/catalog first as C, then sign metadata referring to C and publish that
metadata in a later commit. This avoids a self-referential commit identity.

## Root rotation, rollback, expiry and compromise

Use the library's complete root → timestamp → snapshot → targets update
workflow. Persist trusted roots as each successor is verified. Root N+1
requires both the old and new root thresholds and the exact successor version.
Keep intermediate roots available; bounded rotation loops can resume on a
later explicit refresh. An expired bootstrap root may establish a chain to a
fresh root; it is not grounds to skip verification.

Persist trusted role versions/digests and time state in OS-protected storage.
Maintain equality consistency as well as rollback checks: same trusted
version/different authenticated content is a publication error/rejection.
Timestamp/snapshot/targets versions must agree through the verified chain,
and target bytes must agree with that chain's hashes and lengths.

Do not add a naive permanent global version floor that prevents TUF's
specified recovery after rotation of compromised online keys. Follow the
library/specification's role-specific invalidation/recovery rules. Application
catalog/manifest revision floors are scoped to the current root-authorized
targets-key-set identity. That identity changes only through a verified root
authorization change, not an unsigned reset, GitHub tag, timestamp signer or
higher manifest revision. Resetting an application floor is permitted only as
that explicit new authorization era, with the root transition durable first.
Ordinary root renewal with unchanged targets authorization does not reset it.

Proposed expiry policy: root 12 months with renewal well before expiry,
targets/catalog publication authorization at most 30 days, snapshot at most
7 days, timestamp at most 24 hours. Timestamp may refresh against unchanged
approved target bytes. Shorter values are permitted; publication automation
must maintain availability without acquiring targets authority.

Use one fixed update-start time. Require reasonable device wall time and keep
a protected last-successful-time lower bound; a clock moving backward cannot
extend metadata validity. A future clock can cause denial of service; do not
“repair” it by trusting HTTP Date or silently disabling expiration. Request
clock correction/refresh while preserving the local fallback.

Offline policy:

- A previously fully verified, unexpired, compatible cached target may be
  explicitly armed after revalidation of its cached authorization and current
  donor/runtime. Offline means not freshly checked for revocation.
- Expired downloaded authorization is not eligible for a new Arm. No
  allow-expired override is part of the initial v2 updater.
- An already Armed investigation pins its configuration. Expiry does not
  mutate it, reinstall instrumentation or interrupt capture; record
  valid-at-arm/expiry/capture facts. Stop/rearm requires current admission.
- Offer the independently pinned bundle as a labelled fallback; never silently
  autoarm it. A digest already known revoked cannot be silently resurrected by
  cache fallback, including a matching bundled digest.
- Persistent security-state corruption/loss does not reset trust to “version
  zero and accept anything.” With a protected trusted head intact, refetch
  against it or use the bundle. If that head is unavailable after reinstall,
  re-signing, access-group change or backup restore, disable downloaded
  activation pending explicit bootstrap recovery; do not claim uninterrupted
  rollback protection.
- Initial installation has no history before its bootstrap. Offline clients
  cannot discover a revocation withheld forever. Cache/file-system controls
  cannot defend against a fully compromised OS restoring all trusted state.

Revocation removes targets from a newer authenticated catalog and records
revoked digests. Persist a bounded denial set for the current authorization
era; do not revive a known-revoked digest from an older slot. Capacity exhaustion
fails closed and needs a reviewed root-authorized recovery transition, not
silent eviction of denial history.

One stolen online timestamp/snapshot key must not authorize new configurations.
Rotate compromised role keys with the surviving offline root threshold and
apply standard recovery rules. A compromised targets threshold can authorize
malicious configurations within compiled limits; revoke it through root
rotation and a clean catalog. Compromise/loss of the root threshold has no
self-authenticating in-band recovery: a new independently trusted ordinary
Streamside update/root bootstrap is required. Retain signing/publication
history for incident review.

## GitHub distribution and publication

| Distribution option | Assessment |
| --- | --- |
| GitHub Releases | Human-friendly bundles and audit artifacts. Ordinary assets/tags can be mutable. GitHub immutable releases add useful platform protections and release attestations, but GitHub remains outside signing authorization. Downloads often require CDN redirects, increasing policy surface. |
| Full immutable repository revisions | Preferred target transport. A signed targets record identifies a full target commit and exact bytes; no latest/tag/branch name is an authority. Raw URLs permit a smaller fixed-host transport with redirects disabled. |
| Mutable repository location for metadata discovery | Permitted untrusted locator only. Signature/expiry/version checks decide acceptance. A malicious branch/CDN can deny/freeze responses within the expiry window, not authorize new bytes. |

[GitHub's immutable-release documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
describes tag/asset protections and attestations. They are defense in depth;
the client still checks independent targets signatures and exact bytes.

Proposed compiled transport: HTTPS only, port 443, raw.githubusercontent.com,
fixed owner/repository and a fixed diagnostics-registry metadata locator.
No GitHub API latest-release search or user-supplied mirror. Versioned root,
timestamp/snapshot/targets metadata are fetched through the fixed locator.
Verified targets custom.source_commit selects the full-hex target commit,
and only the compiled diagnostics/registry/v2/targets prefix is used.
No downloaded destination changes that policy. Redirects are disabled; a
hosting change needing another host requires a reviewed binary policy update.

Publish in this order:

1. Review manifest/catalog diffs, native schema/capability/budget checks and
   target digests. Commit target files and consistent-snapshot aliases as C.
2. Independent targets signers approve the exact metadata binding C and the
   raw file digests. Neither a repository merge nor an Actions OIDC identity
   substitutes for that authorization.
3. A restricted signer produces snapshot metadata binding approved targets.
   Publish immutable versioned metadata/targets first, then timestamp last.
   Reject attempted overwrite of any already published version/path/digest.
4. Preserve raw signed envelopes, exact target bytes, full commit identities,
   reviewer approvals and optional Sigstore provenance in release/audit bundles.
   A failed/partial publish leaves clients on a prior verified generation.
5. Timestamp renewal references an existing approved snapshot. CI cannot
   create new targets authorizations or silently move reviewed asset identity.

Use Sigstore/GitHub attestations to audit which workflow published which
digests and to monitor unexpected publication. They do not replace offline
targets authorization. [Sigstore's threat model](https://docs.sigstore.dev/about/threat-model/)
distinguishes proof of signing identity from the policy decision to trust it.

## Retrieval, budgets and persistent storage

One explicit refresh/download transaction at a time; no background polling,
startup auto-refresh, parallel target fan-out or unbounded retry queue.
No decompression/archive extraction. Bound streamed bytes even when headers
lie or are absent; reject excess before allocation/JSON processing.

Proposed compiled v2 transport ceilings:

| Item | Maximum |
| --- | --- |
| HTTP request / overall refresh | 10 seconds/request, 30 seconds/operation; no automatic retry |
| Outstanding refresh / HTTP requests | One operation, one request, one coalesced UI update |
| Redirects / credentials | Zero redirects; ephemeral session, no cookies, auth challenges or GitHub tokens |
| Root / timestamp / snapshot / targets metadata | 16 / 4 / 8 / 32 KiB per file |
| Catalog / individual manifest | 16 KiB each; at most 64 listed entries |
| Root successors per refresh | Four; commit each verified root, resume safely on a later refresh |
| Selected downloaded manifests retained | At most two; bundle lives in binary |
| Network bytes per operation | 192 KiB total, including rotation probes/target downloads |
| JSON and names | Depth ≤8; at most 16 keys, 8 signatures/file, 4 top-level roles, 64 targets/catalog entries; manifest parser remains ≤256 native tokens and bounded strings |
| Writable persistent registry storage | ≤256 KiB total including committed generations, security journal and staging; not 256 KiB per slot |
| Active runtime limits | Existing compiled limits unchanged: two lists, 128 shared entries, 2 ms callback work, current event/bridge/ring/alias/report ceilings |

F1 accounting remains authoritative. Serialize updater work with export and
active investigation work; M0 must measure and bound the selected library's
heap/queues/FFI copies within the existing aggregate target, with an updater
reservation no larger than 256 KiB and combined owned steady work no larger
than the 512 KiB architecture target. Do not claim these results before the
dependency spike; if it cannot fit, explicitly revisit the dependency/design,
not the recorder's limits. Full-source bootstrap/transient platform costs must
remain separately disclosed as in v1.

Library defaults are not the resource boundary. In particular, the documented
[tough targets-size setting](https://docs.rs/tough/latest/tough/struct.Limits.html)
is a fallback when signed length is absent; it is not an unconditional cap.
The transport must reject a signed advertised length above the compiled ceiling
and enforce the same ceiling on streamed bytes regardless of signature validity.
The [reference updater](https://theupdateframework.readthedocs.io/en/latest/api/tuf.ngclient.updater.html)
also illustrates why default automatic refresh/retries cannot be inherited
without a controlled adapter. Our explicit-only/no-retry policy is deliberate.
Use [Ed25519 standard vectors](https://www.rfc-editor.org/rfc/rfc8032.html) as
crypto interoperation evidence; never turn their example keys into production
bootstrap trust.

Path rules: decode once, enforce the ASCII grammar for the particular metadata
or catalog target, reject empty/dot segments, .., backslashes, absolute paths,
encoded separators, percent ambiguity, NUL, queries/fragments, symlinks and
non-hex commit strings. URL construction never concatenates an arbitrary
signed URL. A valid signature cannot authorize a new host. Recheck policy in
the transport callback even for library-generated requests.

Persistent state separates two transactions:

1. **Security head:** trusted root/role versions/digests, authorization identity,
   time floor and revocations. Update durably as verification advances, using
   the library's specified rollback state plus an OS-protected head/journal.
   Cancellation or target-download failure must not roll this state backward.
2. **Selectable catalog generation:** exact verified envelopes/catalog/targets,
   digests, lengths, compatibility results and provenance. Stage under random
   local transaction names, fsync files, write the manifest of the complete
   generation, atomically replace the selection pointer and sync the directory.
   Cache readers see one committed generation; no partial promotion.

The protected head is a ≤32 KiB versioned record containing repository/channel,
root version/digest, targets authorization identity, trusted role versions/raw
digests, catalog version/digest, per-ID revision/digest floors, revoked digests,
last trusted UTC lower bound and committed-generation digest. It contains no
diagnostic evidence. Validate it against its embedded/rotated root and bounded
schema when loading; OS protection anchors its anti-rollback integrity.
Store cache slots only under the app container's fixed
Library/Application Support/Streamside/diagnostic-registry/v2 directory.
The library's separate datastore may not create an unaccounted second cache.

M4 must define the precise POSIX/Apple storage adapter and failpoints. Two
bounded slots can retain current/previous selection state, but a previous slot
is usable only if it still satisfies the current durable security head. It is
not a rollback escape hatch. Enforce the total 256 KiB reservation before
staging; evict unpinned target blobs or fail with the prior valid selection.
Root chains are processed one successor at a time, not accumulated unboundedly.

Use iOS-protected application storage, atomic same-filesystem replacement, no
following symlinks, and an OS-protected trusted head (Keychain/access group
feasibility is an M0 gate for sideloaded and jailbreak distributions).
A filesystem attacker may corrupt/delete the cache but cannot lower the
protected trusted head under this threat model. Do not rely on an app-writable
JSON version number as tamper-resistant rollback protection.

On crash after security-head advance but before selection promotion: recover
the committed generation only if still authorized; otherwise show unavailable
downloaded configuration, retain bundle access, and resume verification on the
next explicit refresh. Never roll the head back to make the old slot work.
Test every write/flush/rename/head-commit boundary, including no space and
protected storage unavailable. ETags/304/cache age are transport hints, never
authentication or freshness authorities.

## Update and activation state machine

~~~mermaid
stateDiagram-v2
  [*] --> Bundled
  Bundled --> Refreshing: explicit refresh while Dormant
  Verified --> Refreshing: explicit refresh while Dormant
  Expired --> Refreshing: explicit refresh while Dormant
  Refreshing --> Verifying: bounded metadata/target bytes
  Verifying --> Staging: valid trust chain and exact target hashes
  Staging --> Verified: durable atomic commit
  Refreshing --> Prior: timeout/cancel/background
  Verifying --> Rejected: signature/rollback/expiry/schema failure
  Staging --> Prior: interrupted cache transaction
  Verified --> Selected: explicit compatible selection while Dormant
  Selected --> Armed: existing Arm with fresh admission
  Armed --> Capturing: existing Capture
  Capturing --> Armed: completion/partial result
  Armed --> Selected: existing Stop acknowledgment
  Verified --> Expired: authorization expiration
~~~

Prior means the last generation still valid under the durable security head,
otherwise the explicitly labelled bundle. Rejected is a refresh outcome,
not permission to overwrite valid cache or silently switch the selection.
Downloaded status and compatibility are independent axes: “authenticated but
incompatible” is meaningful and cannot be armed.

Initial v2 scheduling policy: refresh is unavailable while Armed/Capturing/
Stopping or exporting. It returns a clear Busy reason without changing them.
If Arm arrives during a Dormant refresh, cancel the refresh, retain safe
committed trust state, and arm the already selected admitted configuration.
No network/crypto job runs through high-frequency capture work. Foreground/
background and resource-safety events cancel the update generation; stale
callbacks cannot commit or activate. No automatic restart/resume/rearm occurs.

Refresh does not select or activate. Selection does not Arm. A refresh result
never mutates an existing lease, source generation or frozen report.
A future relaxation permitting background refresh during Armed operation would
need its own perturbation evidence; it is not required for the no-rebuild goal.

UI distinguishes:

- Built-in: revision/source and binary SHA-pin verification.
- Downloaded and verified: revision, publication commit, verification time,
  validity/expiry, currently selected versus merely available.
- Expired or clock uncertain: unavailable for new Arm; explain refresh/clock
  recovery and labelled bundle availability.
- Authentic but incompatible: specific missing compiled capability/version,
  schema, donor/Hermes ABI/profile or narrowed operational constraint.
- Rejected refresh: fixed understandable signature/integrity/rollback/size/
  network/storage reason; prior valid configuration remains selected.
- Busy/cancelled: collection/export/lifecycle took priority.

Do not expose raw exception objects, credentials, full request URLs or capture
data in UI failures. Preserve Arm/Capture/Stop meaning and general logger
independence. Reports pin the selected target digest, TUF role versions/
authorization identity/source commit, validity-at-arm and actual resource bounds
at capture time, not whatever the updater knows when the user later exports.

## Threat model and required negative tests

| Threat / failure | Control and expected result |
| --- | --- |
| GitHub writer/CDN/TLS response compromised | Treat bytes/locators as untrusted; cannot authorize target bytes without the pinned root's targets threshold. Denial of service remains possible. |
| Invalid signature, unauthorized key, wrong role/repo/channel, duplicate signer | Fail threshold/domain checks before admission; do not retain the candidate as verified. |
| Canonicalization/duplicate-key/encoding ambiguity | Library vectors and strict bounded application parsing; no parser disagreement can substitute signed values. |
| Old metadata/targets replay, same-version fork | Durable role/application floors and digest consistency; reject without lowering the security head. |
| Freeze / expired timestamp / bogus clock | Expiry at fixed trusted update-start time; no unsafe-expiry mode, HTTP-time trust or silent cached resurrection. |
| Mix-and-match snapshot, targets, catalog or commit | Verify versions, raw hashes and lengths throughout one chain; catalog entries and targets custom commit must agree. |
| Online key stolen | Cannot create targets authorizations; rotate via surviving root keys and standard recovery path. |
| Targets threshold stolen | Config authority remains confined to compiled behavior; root rotates authorization, revokes bad digests and publishes a clean generation. |
| Root threshold compromised/lost | Explicit out-of-band trusted binary/root recovery; no pretend in-band cure. |
| Root rotation gap/duplicate/skipped version/new-root-only signatures | Verify every N+1 with old and new thresholds; persist progress, bound work, reject bad transition. |
| Partial download, forged Content-Length, huge JSON/deep arrays, endless stream | Enforce incremental byte/time/token/depth/concurrency bounds and abort before expensive work/admission. |
| Traversal, URL redirection, encoded path, symlink, new endpoint | Compiled transport/storage policy rejects even if signed; no arbitrary destinations. |
| Corrupt/modified cache, missing files, trusted-head failure, offline startup | Reverify bytes/authorization, fail closed for remote activation, retain labelled independent bundle where not revoked. |
| Crash/kill/no space between transaction steps | Failpoint replay shows old authorized or new complete generation only; durable security floors never decrease. |
| Concurrent refresh/Arm/Capture/Stop/export/background | Existing commands win, one update generation/copy, no lease mutation, stale completion cannot promote or transmit anything. |
| Validly signed missing capability, donor mismatch, unsupported schema/semantics, expanded limits | Native admission rejects; no signature override or descriptor expansion. |
| Malicious config attempts report disclosure | No evidence API in updater and no upload operation; request audit contains only compiled metadata/target reads. |
| Revoked entry reintroduced from old cache/bundle | Denial state prevents silent reactivation; explicit corrective newer target or root-authorized recovery is required. |
| Process/OS compromise or full secure-state rollback | Outside cryptographic client protection; disclose trust/storage limits instead of claiming hardware monotonicity. |

Test known-good vectors independently with python-tuf and the pinned client.
Add metamorphic tests changing a single authenticated hash/version/role/domain,
parser fuzzing and signature-validation negatives. Run client conformance and
Streamside policy tests separately so application restrictions are not hidden
as unexplained conformance skips.

## Finite implementation milestone

V2 source implementation starts only as a separately authorized milestone.
Its completion criterion is compatible new bytes accepted without another IPA,
not deploying a duplicate pinned fallback.

| Item / dependency | Concrete deliverable and completion gate |
| --- | --- |
| M0 — dependency and storage feasibility | Pin the client/crypto/test versions; reproducible aarch64 iOS static-link and C ABI smoke test; bounded transport/cancellation and allocation measurements; protected trusted-head behavior under real sideload/signing contexts. Record licensing/security review and mandatory conformance results. Stop on an unresolved fit/trust blocker. |
| M1 — trust bootstrap and publisher, after M0 | Offline root/targets ceremony, role/key/threshold/expiry policy, deterministic standard metadata/target builder, exact-byte review/sign/publish workflow and rotation/revocation/recovery runbook. No private root/targets keys available to GitHub publication jobs. Test interoperation and wrong-role/domain vectors. |
| M2 — verifier/admission boundary, after M0/M1 | Standard trust-chain verification plus strict authenticated catalog/schema-2 manifest adapter, reusing legacy bounded validators; newly reviewed configuration IDs are data while capability/hook/donor/profile IDs remain compiled; no alternate executable paths. All signature/rollback/freeze/mix-and-match, native compatibility, semantic-version and resource-expansion negatives pass. |
| M3 — bounded GitHub retrieval, after M2 | One explicit fixed-host transaction; streaming byte/time/path/redirect controls; fault-injected network and cancellation tests. No evidence dependency or report uploads. |
| M4 — persistent trust/cache transaction, after M2/M3 | Durable protected security head, bounded exact-byte cache, crash/space/corruption/backup-state tests at every commit boundary. Offline/expired/revoked fallback behavior matches this design. |
| M5 — selection/UI/runtime integration, after M4 and accepted v1 | Controlled refresh/select and immutable lease identity; existing commands/compiled donor gates unchanged. Concurrency tests cover Arm/Capture/Stop/export/lifecycle. No diagnostics-only hooks or reset/reinstall used to apply a manifest. |
| M6 — end-to-end device/security acceptance and release reconciliation | One installed ordinary v2 runtime first uses bundle A, then downloads independently signed reviewed schema-2 configuration B with a new configuration ID and different bytes/parameters, arms it on the same mounted chat, captures/exports correct B provenance, stops, restarts offline and uses unexpired verified B. IPA/framework/HBC executable identities remain unchanged between A and B. Negative distribution/rotation/crash/offline tests pass; device overhead meets declared ceilings; reviewers inspect threat boundaries; documentation reconciles only at freeze. |

Additional M6 acceptance invariants:

- Wrong signatures/keys and authentic unsafe/incompatible B are rejected.
- Root and targets rotations work without an app reinstall while old trust is
  intact; compromised-root recovery is explicitly outside that guarantee.
- Refresh during active investigation does not interrupt it; stale refresh
  callbacks cannot change selection or evidence.
- Expired or revoked downloaded B cannot newly arm through offline/cache
  fallback. Available bundled fallback is labelled and explicit.
- New capability/code/hook requirements are reported as needing a normal
  Streamside update, never worked around by remote execution.
- F1–F6 v1 completion does not itself count as any M0–M6 updater acceptance.
  Conversely, v2 planning does not reopen chat-gap diagnosis or block recording
  v1's narrower supported scope once its own evidence exists.

No v2 keys, binaries, publication jobs or network/cache implementation were
created by this architecture record. Dependencies, security assumptions and
acceptance gates are explicit; unperformed library/device feasibility remains
future evidence, not an implicit pass.
